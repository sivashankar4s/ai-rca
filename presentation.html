The Problem

Manual RCA is slow,
error-prone & deep-knowledge-dependent

Every time a data-pipeline failure hits dp_monitor_db11224, engineers repeat the same 4-step manual process.

  • 1
    Query Athena manually Write SQL against the monitoring table, filter by status=FAILED, guess the right time window. Takes 10–20 min per investigation.
  • 2
    Author CloudWatch Insights queries from scratch Must know the log group names, error field names, and component names. Senior knowledge required. Mistakes lead to zero results.
  • 3
    Read through hundreds of log lines Manually correlate log lines with file_trace_ids, device IDs, and error codes. High cognitive load, easy to miss patterns.
  • 4
    Write the RCA report Document root cause, impacted count, suggested fix, and escalation path. Takes another 30–60 min after the investigation.
Total time per incident: 1–3 hours of senior engineer time. With multiple concurrent failures this becomes the biggest drag on on-call rotation.

The Solution

AI-RCA automates the entire
investigation pipeline

A two-step web UI backed by a FastAPI service that orchestrates Athena, CloudWatch, and an LLM.

🔍

Step 1 — Fetch

Select a time range (1h / 1d / 1w) or pick custom date pickers. Optionally filter by component name, file name, or trace ID. AI-RCA queries Athena and returns a paginated failure table in seconds.

🧠

Step 2 — Analyze

Select one or more failed entries from the table, click "Analyze Root Cause." The backend automatically searches AWS CloudWatch logs for those records and feeds them to the LLM, which summarizes the root cause, groups failures by pattern, and returns a structured report — no manual log hunting required.

📋

Failure Groups

Each group has: error pattern, root cause (2–3 sentences), failure category, impact count, immediate action, likely fix, affected files, and escalation path — all specific to actual field values.

📝

Executive Summary

A 2–3 sentence human-readable report ready to share with stakeholders. Generated automatically alongside the failure groups — zero manual writing. Model accuracy is tunable: the Config panel lets you switch between any available LLM (Claude, Titan, etc.) at runtime to balance speed, cost, and accuracy for your use case.

🔗

CloudWatch Deep-Links

Every failure group includes a direct CloudWatch Logs Insights URL pre-populated with the right query, log group, and time window. One click — no manual setup.

💾

Snapshot & Audit Trail

Every Athena result is auto-saved to ./snapshots/ with a timestamped filename. Supports local dev mode with static JSON — no AWS credentials needed.

AI Pipeline

What the LLM does — 5 steps,
each with a precise job

The RCAOrchestrator chains LLM invocations (and an optional code analysis agent) with actual failure data injected into each prompt.

1

Failure Summarization · max_tokens=1024

Injects up to 50 failure records as JSON. Asks the LLM to identify: failing components, exact error codes (e.g. S3_PUT_FAILED), pipeline stage clustering (e.g. lz-processor), time-based bursts, and environmental signals (device IDs, tenant aliases). Output feeds directly into LLM call 2 as context.

2

CloudWatch Query Generation · max_tokens=768

Injects the failure summary + extracted error_codes, component names, and file_trace_ids. Generates exactly 3 Insights queries: (1) error code search across all fields, (2) component + ERROR/WARN filter with stack traces, (3) trace ID correlation to show the full execution path. Returns a raw JSON array — no markdown.

3

RCA + Failure Grouping · max_tokens=4096

Injects failure records + summary + collected CloudWatch log lines. Produces a structured JSON array of FailureGroup objects with: root_cause (2–3 sentences with real field values), immediate_action (single most important step RIGHT NOW), likely_fix (specific code/config change), affected_files (Lambda functions, Terraform files, config repos), escalation_path, and log_samples (3 actual log lines).

4

Executive Summary · max_tokens=1024

Injects the full set of FailureGroup results from step 3. Produces a concise, leadership-facing summary of overall impact, the most urgent failure groups, and recommended next actions — ready to paste into a status update or incident report.

5

Code Analysis Agent · via GitHub MCP

On the Source Code Intelligence page, fetches a PR or branch diff via the GitHub MCP Server and sends it to Claude with a structured review prompt. Returns a JSON summary + findings[] covering security, sql_injection, sonar-style code smells, formatting, and feature recommendations — each finding ranked by severity (critical → info).

Guardrails: All prompts explicitly demand actual field values (component_name, error_code, stage, device_id). Vague responses like "check the logs" are prohibited in the prompt instructions. JSON extraction uses a robust regex fallback if the LLM wraps output in markdown fences.

New · Source Code Intelligence

From "why did it fail" to
"is the fix any good"

A GitHub MCP integration brings repo, branch, and PR awareness into the app — and an AI Code Review agent inspects diffs the moment they're ready.

🔗

Repo & Branch Browser

Lists repo info, branches, and open pull requests via the GitHub MCP server (list_branches, list_pull_requests, search_repositories) — no manual GitHub UI hopping.

🛡

AI Code Review

One click on a branch or PR fetches its diff (pull_request_read / get_commit) and sends it to Claude for analysis.

📋

Severity-Ranked Findings

Results rendered as a summary + a list of findings — each tagged with severity (critical/high/medium/low/info), category, file, line, description, and a concrete recommendation.

What the AI Code Review checks for

🛡

Security

Hardcoded secrets, unsafe deserialization, missing auth checks, insecure defaults.

🗄

SQL Injection

String-formatted or concatenated queries that should be parameterized.

📐

SonarQube-Style

Code smells, duplication, complexity, dead code, missing error handling.

🎨

Formatting

Style/convention deviations from the rest of the codebase.

💡

Feature Ideas

Suggested enhancements or follow-ups based on what the diff is doing.

Endpoints: GET /api/github/pull-requests/{number}/review and GET /api/github/branches/review?branch=... — both return a CodeReviewResult (repo, target, summary, findings[]) consumed directly by the Source Code Intelligence page in the UI.
